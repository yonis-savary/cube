# Models

A model is a class describing one table : its name, its fields and its relations. From that single
description Cube gives you queries, validation rules, JSON output and TypeScript types — and since
models are generated from your database, you rarely write one by hand.

```php
$product = Product::insertArray(['name' => 'screen', 'price_dollar' => 20]);

$product->name = 'monitor';
$product->save();

Product::select()->where('price_dollar', 20, '>')->fetch();
Product::find(1);
Product::deleteId(1);
```

## Generating your models

Write your tables in a migration, apply it, and let Cube write the classes

```bash
php do make:migration AddProductTable   # create the migration file
php do migrate:migrate                  # apply it, then regenerate the models
php do models:generate                  # regenerate the models only
```

`migrate:migrate` regenerates your models once the migrations are applied, so your classes never
drift from your schema. Use `php do migrate:migrate -s` (or `--skip-generation`) to skip that step.

Add `--apis` (or `-a`) to also write a [`ModelAPI`](./107-controller-and-apis.md) subclass per
model in `Http/Apis`, `ProductAPI` for `Product`. An API file that already exists is never
rewritten, so your overrides are safe, and the framework's own tables (prefixed with `__`) get none

```bash
php do models:generate --apis
```

Everything the generator owns is marked with the `#[Generated]` attribute, and **your own methods
are preserved** : on regeneration, methods without that attribute are copied over, along with the
`use` statements of the file. So you can safely add behaviour to a generated model, as long as you
never touch a `#[Generated]` member.

Generated classes also carry `@property` annotations, which is what makes `$product->name`
autocomplete in your IDE.

```php
/**
 * Generated by `Cube\Data\Models\ModelGenerator\Table`
 * @property int $id
 * @property string $name
 * @property ProductManager[] $managers
 */
class Product extends Model
{
    #[Generated]
    public static function table(): string
    {
        return 'product';
    }

    #[Generated]
    public static function primaryKey(): string
    {
        return 'id';
    }

    /**
     * @return array<string,ModelField>
     */
    #[Generated]
    public static function fields(): array
    {
        return [
            'id' => (new ModelField('id'))->type('INTEGER')->nullable()->hasDefault(true),
            'name' => (new ModelField('name'))->type('STRING')->notNull()->hasDefault(false),
        ];
    }

    #[Generated]
    public static function relations(): array
    {
        return ['managers'];
    }
}
```

A model needs `table()`, `fields()` and `relations()` ; `primaryKey()` returns `null` by default,
and methods needing an id (`find()`, `deleteId()`, `last()`, `updateRow()`) throw without one.

## Fields

A field is a `ModelField`, described once and reused everywhere : the migration schema, the
validation rules, the JSON conversion and the generated TypeScript types all read the same object.

```php
ModelField::id();                                  // integer, auto-increment, primary key
ModelField::string('name', 255)->notNull();
ModelField::integer('stock')->default(0);
ModelField::float('weight')->nullable();
ModelField::boolean('active');
ModelField::decimal('price', 10, 2);
ModelField::date('released_on');
ModelField::datetime('created_at')->generated();
ModelField::timestamp('updated_at');

ModelField::integer('agency_id')
    ->references(Agency::class, 'id')
    ->onDeleteCascade()                            // or ->onDeleteSetNull()
;

ModelField::string('email')->unique();
```

Two flags change how a field behaves when saving : a `generated()` field is never written (the
database computes it), and a field with a `default()` is skipped when its value is `null`.

Field values are also **parsed when read** : an `INTEGER` field gives you an `int`, a `DATE` or
`DATETIME` field gives you a `DateTime`, and `toArray()` formats it back to `Y-m-d H:i:s`.

## Reading

```php
Product::find(1);                          // by primary key, or null
Product::find(1, ['managers']);            // and load the relation
Product::findWhere(['name' => 'screen']);  // first match, or null
Product::findOrCreate(['name' => 'screen']);
Product::exists(1);
Product::existsWhere(['name' => 'screen']);
Product::last();                           // highest primary key, or null on an empty table
Product::select()->where('name', 'screen')->first();
```

`select()`, `insert()`, `update()` and `delete()` return a `Query` you can keep building — see
[Database and queries](./110-database-and-queries.md) for the query API

```php
Product::select()
    ->where('price_dollar', 20, '>')
    ->order('name', 'ASC')
    ->limit(10)
    ->fetchBunch()
;
```

## Writing

```php
// Insert from an array
$product = Product::insertArray(['name' => 'screen', 'price_dollar' => 20]);

// Or build then save
$product = new Product(['name' => 'mouse']);
$product->save();

// Update
$product->name = 'monitor';
$product->save();

// Update several fields at once
$product->merge(['name' => 'monitor', 'price_dollar' => 25])->save();
$product->patch(['name' => 'monitor']);   // merge + save
Product::updateRow(1, ['name' => 'monitor']);

// Delete
$product->destroy();
Product::deleteId(1);
Product::deleteWhere(['name' => 'mouse']); // returns the deleted models
```

`save()` updates a model read from the database (or already saved once) and inserts any other,
even when you filled its primary key yourself. An update targets the row through the primary key
the model was read with, so changing the key and saving renames that row rather than another one.
It only writes the fields that actually changed — models keep their original values in memory for
that — and skips `generated()` fields. `DateTime` values are written as `Y-m-d H:i:s`, or `Y-m-d`
for a `DATE` field.

A few more methods worth knowing

```php
$product->reload();      // re-read the row (and the loaded relations)
$product->replicate();   // deep copy, primary keys stripped, ready to be saved
$product->anonymize();   // drop the primary keys in place
$product->toArray();     // model + loaded relations, as a nested array
```

## Relations

Relations are declared as methods returning `hasOne()` or `hasMany()`, and listed in `relations()`.
The generator writes them for you from your foreign keys, naming a `HasOne` after its column with a
leading underscore

```php
#[Generated]
public function _agency(): HasOne
{
    return $this->hasOne('_agency', 'agency_id', Agency::class, 'id');
}

#[Generated]
public function managers(): HasMany
{
    return $this->hasMany('managers', ProductManager::class, 'product', 'id');
}
```

Relations are **not** loaded until you ask for them ; reading one that was never loaded throws

```php
$product = Product::find(1);
$product->load('managers');               // loads the relation
$product->managers;                       // ProductManager[]

$product->load('managers.someRelation');  // nested, with dot notation
$product->loadMissing('managers');        // only loads what is not loaded yet
```

You can also load them while reading

```php
Product::find(1, ['managers']);
Product::findWhere(['name' => 'screen'], ['managers']);
Product::select(['_agency'])->fetch();
Product::select()->with('_agency')->fetch();
```

`with()` on a query turns the relation into a `LEFT JOIN`, so it only handles `HasOne` relations —
asking for a `HasMany` there logs an error and loads nothing. Use `find()`/`findWhere()` with a
`$with` list, or `load()`, when you need collections.

Relations also work the other way around : data given to the constructor is bound, and saved with
its parent

```php
$product = Product::insertArray([
    'name' => 'screen',
    'managers' => [
        ['manager' => 'Bob'],
        ['manager' => 'Alice'],
    ],
]);
```

Saving the parent sets the foreign key on each bound child and saves it, so a whole tree is
inserted in one call. `replicate()` follows the same tree, which makes duplicating an aggregate a
one-liner.

## Models at the HTTP boundary

`toObjectParam()` projects your fields into validation rules, so a model can validate a request and
build itself from it

```php
// In a controller
$product = Product::fromRequest($request);              // validated, primary key refused
$product = Product::fromRequest($request, ['agency_id' => $agency->id()]);
$product->save();

$product = Product::fromArray($data);                   // same, from an array

// The rules themselves, if you want them in a Request subclass
Product::toObjectParam();                               // fields + relations
Product::toObjectParam(nullable: true, withRelations: false);
```

In those rules a field is optional when its column is nullable or has a database default, and so
are the relations : only the columns an insert cannot do without are required.

Returning a model (or a `Bunch` of models) from a controller is enough : the router converts it to
JSON with `toArray()`. And a `Model`-typed parameter in a route callback is fetched from the slug
automatically — see [Routing and middlewares](./106-routing-and-middlewares.md).

For a full CRUD API over a model, let your controller delegate to a `ModelAPI` instead of writing
the queries by hand — see [Controller and APIs](./107-controller-and-apis.md).

## Reacting to a save

Every model is an event dispatcher, and emits `SavedModel` after each successful save — insert or
update. On an insert the model has already been reloaded, so the generated id and the database
defaults are available

```php
$product = new Product(['name' => 'screen']);

$product->onSaved(function (SavedModel $event) {
    Cache::getInstance()->delete('product-'.$event->created->id());
});

$product->save();
```

`onSaved()` subscribes to **one instance**, which is what you want for a one-off follow-up, and
what relations use internally to save bound children after their parent.

## Sharing your types with the front-end

```bash
php do models:to-types
```

Generates a TypeScript file exporting one type per model, fields and relations included, so your
front-end reads the same descriptions as your back-end.
