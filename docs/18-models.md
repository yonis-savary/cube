# Models

A model is a class describing one table : its name, its fields and its relations. From that single
description Cube gives you queries, validation rules, JSON output and TypeScript types — and since
models are generated from your database, you rarely write one by hand.

```php
$product = Product::insertArray(['name' => 'screen', 'price_dollar' => 20]);

$product->name = 'monitor';
$product->save();

Product::select()->where('price_dollar', 20, '>')->fetch();
Product::find(1);
Product::deleteId(1);
```

## Generating your models

Write your tables in a [migration](./17-migrations.md), apply it, and let Cube write the classes

```bash
php do make:migration AddProductTable   # create the migration file
php do migrate:migrate                  # apply it, then regenerate the models
php do models:generate                  # regenerate the models only
```

`models:generate` reads every table of your database and writes one class per table in the
`Models/` directory of your application (it asks which one when you have several), `Product` for
`product`, `ProductManager` for `product_manager`. The migration table gets one too. Once the files
are written, it dispatches the `GeneratedModels` event.

`migrate:migrate` runs this generation once the migrations are applied, so your classes never drift
from your schema. Use `php do migrate:migrate -s` (or `--skip-generation`) to skip that step. In
production it is always skipped : the models you deploy are the ones you generated and committed.
A table or a column whose name is not a plain identifier (letters, digits, underscores) makes the
generation throw, since names are written into PHP source.

Add `--apis` (or `-a`) to also write a [`ModelAPI`](./19-model-apis.md) subclass per model in
`Http/Apis`, `ProductAPI` for `Product`. An API file that already exists is never rewritten, so your
overrides are safe, and the framework's own tables (prefixed with `__`) get none

```bash
php do models:generate --apis
```

Everything the generator owns is marked with the `#[Generated]` attribute, and **your own code is
preserved** : on regeneration, the methods without that attribute are copied over, along with the
`use` statements of the file and the traits the class uses. So you can safely add behaviour to a
generated model, as long as you never touch a `#[Generated]` member — change the migration and
regenerate instead.

Generated classes also carry `@property` annotations, which is what makes `$product->name`
autocomplete in your IDE.

```php
/**
 * Generated by `Cube\Data\Models\ModelGenerator\Table`
 * @property int $id
 * @property string $name
 * @property string $price_dollar
 * @property ProductManager[] $managers
 */
class Product extends Model
{
    #[Generated]
    public static function table(): string
    {
        return 'product';
    }

    #[Generated]
    public static function primaryKey(): string
    {
        return 'id';
    }

    /**
     * @return array<string,ModelField>
     */
    #[Generated]
    public static function fields(): array
    {
        return [
            'id' => (new ModelField('id'))->type('INTEGER')->nullable()->hasDefault(true),
            'name' => (new ModelField('name'))->type('STRING')->notNull()->hasDefault(false),
            'price_dollar' => (new ModelField('price_dollar'))->type('DECIMAL')->nullable()->hasDefault(true),
        ];
    }

    #[Generated]
    public function managers(): HasMany
    {
        return $this->hasMany('managers', ProductManager::class, 'product', 'id');
    }

    #[Generated]
    public static function relations(): array
    {
        return ['managers'];
    }

    // Not generated : kept as is on the next generation
    public function getPriceWithTax(float $taxRate = 0.2): float
    {
        return $this->price_dollar * (1 + $taxRate);
    }
}
```

A model needs `table()`, `fields()` and `relations()` ; `primaryKey()` returns `null` by default,
and the methods needing an id (`find()`, `exists()`, `deleteId()`, `last()`, `updateRow()`) throw a
`MissingModelPrimaryKeyException` without one.

## Fields

A field is a `ModelField`, described once and reused everywhere : the migration schema, the
validation rules, the JSON conversion, the generated TypeScript types and the
[API documentation](./15-api-documentation.md) all read the same object.

```php
ModelField::id();                                  // integer, auto-increment, primary key
ModelField::string('name', 255)->notNull();
ModelField::integer('stock')->default(0);
ModelField::float('weight')->nullable();
ModelField::boolean('active');
ModelField::decimal('price', 10, 2);
ModelField::date('released_on');
ModelField::datetime('created_at')->generated();
ModelField::timestamp('updated_at');

ModelField::integer('agency_id')
    ->references(Agency::class, 'id')
    ->onDeleteCascade()                            // or ->onDeleteSetNull()
;

ModelField::string('email')->unique();
```

A field is nullable unless you call `notNull()`. A `generated()` field is never written when saving
(the database computes it). [Migrations](./17-migrations.md#describing-columns) use these same
builders to describe columns.

Field values are **parsed when read** and **formatted when written**

| Type | Read as | Written as |
|---|---|---|
| `INTEGER` | `int` | as is |
| `FLOAT` | `float` | as is |
| `BOOLEAN` | `bool` (`1`, `true`, `t`, `y`, `yes`, `on` are true) | as is |
| `DATE` | `DateTime` | `Y-m-d` |
| `DATETIME` | `DateTime` | `Y-m-d H:i:s` |
| `STRING`, `DECIMAL`, `TIMESTAMP` | `string` | as is |

`toArray()` formats a `DateTime` the same way, so it leaves your application as text.

## Reading

```php
Product::find(1);                          // by primary key, or null
Product::find(1, ['managers']);            // and load the relation
Product::findWhere(['name' => 'screen']);  // first match, or null
Product::findOrCreate(['name' => 'screen']);
Product::exists(1);
Product::existsWhere(['name' => 'screen']);
Product::last();                           // highest primary key, or null on an empty table
Product::last('created_at');               // highest value of another column
Product::select()->where('name', 'screen')->first();
```

`findOrCreate()` inserts the row when nothing matches. Its fourth argument holds values written in
both cases, without being part of the search

```php
$product = Product::findOrCreate(['name' => 'screen'], extrasProperties: ['price_dollar' => 20]);
```

`select()`, `insert()`, `update()` and `delete()` return a `Query` you can keep building — see
[Database and queries](./16-database-and-queries.md#building-queries)

```php
Product::select()
    ->where('price_dollar', 20, '>')
    ->order('name', 'ASC')
    ->limit(10)
    ->fetchBunch()
;
```

Reading a property gives the field value, or the loaded relation of that name. Writing one that is
not a field throws an `InvalidArgumentException` — use `merge()` to ignore the keys a model does not
hold.

## Writing

```php
// Insert from an array
$product = Product::insertArray(['name' => 'screen', 'price_dollar' => 20]);

// Or build then save
$product = new Product(['name' => 'mouse']);
$product->save();

// Update
$product->name = 'monitor';
$product->save();

// Update several fields at once
$product->merge(['name' => 'monitor', 'price_dollar' => 25])->save(); // unknown keys are ignored
$product->patch(['name' => 'monitor']);                              // set + save, every key must be a field
Product::updateRow(1, ['name' => 'monitor']);                        // unknown keys are ignored, returns the row

// Delete
$product->destroy();
Product::deleteId(1);                      // returns the deleted model, or null
Product::deleteWhere(['name' => 'mouse']); // returns the deleted models
```

`merge()` also accepts a `Request`, and then merges its `validated()` values.

`save()` updates a model read from the database (or already saved once) and inserts any other,
even when you filled its primary key yourself. An update targets the row through the primary key
the model was read with, so changing the key and saving renames that row rather than another one.
It only writes the fields that actually changed — models keep their original values in memory for
that — and skips `generated()` fields. An insert skips the `null` fields, leaving them to the
database default, then reloads the row, so the generated id and the defaults are on your model.

Every writing method takes an optional `Database` as its last argument.

A few more methods worth knowing

```php
$product->id();          // the primary key value
$product->reload();      // re-read the row (and the loaded relations)
$product->replicate();   // deep copy, primary keys stripped, ready to be saved
$product->anonymize();   // drop the primary keys in place
$product->toArray();     // model + loaded relations, as a nested array
$product->dataToArray(); // the fields only
```

## Relations

Relations are declared as methods returning `hasOne()` or `hasMany()`, and listed in `relations()`.
The generator writes them for you from your foreign keys :

- a `HasOne` is named after its column, prefixed with an underscore since the column already holds
  that name : `_type` for `user.type`, `_agency_id` for `agency_user.agency_id` ;
- a `HasMany` is named after the referencing class, without the name of the referenced one, in the
  plural : `managers` for `ProductManager` on `Product`, `modules` for `ModuleUser` on `User`.

```php
#[Generated]
public function _type(): HasOne
{
    return $this->hasOne('_type', 'type', UserType::class, 'id');
}

#[Generated]
public function modules(): HasMany
{
    return $this->hasMany('modules', ModuleUser::class, 'user', 'id');
}
```

`hasOne($name, $fromColumn, $toModel, $toColumn)` and `hasMany($name, $toModel, $toColumn, $fromColumn)`
are the two declarations, if you write one yourself.

Relations are **not** loaded until you ask for them ; reading one that was never loaded throws a
`RuntimeException`

```php
$user = User::find(1);
$user->load('modules');                // loads the relation
$user->modules;                        // ModuleUser[]

$user->load('modules._module');        // nested, with dot notation
$user->loadMissing('modules');         // only loads what is not loaded yet
```

A `HasMany` without any row loads an empty array. A `HasOne` loaded through `load()` without a
matching row stays unset, so reading it still throws.

You can also load them while reading

```php
User::find(1, ['modules']);
User::findWhere(['login' => 'root'], ['modules']);
User::select(['_type', 'modules._module'])->fetch();
User::select()->with('_type')->fetch();
```

On a query, a `HasOne` becomes a `LEFT JOIN`, and each `HasMany` costs one more query for the whole
result, not one per row — so loading `modules` on a hundred users runs two queries. Relations can be
nested in any order (`users.modules`, `_user.modules`, `modules._module`). A name that is not in
`relations()` logs an error and loads nothing.

Relations also work the other way around : data given to the constructor is bound, and saved with
its parent

```php
$product = Product::insertArray([
    'name' => 'screen',
    'managers' => [
        ['manager' => 'Bob'],
        ['manager' => 'Alice'],
    ],
]);
```

Saving the parent sets the foreign key on each bound child and saves it, so a whole tree is
inserted in one call. `replicate()` follows the same tree, which makes duplicating an aggregate a
one-liner.

## Models at the HTTP boundary

`toObjectParam()` projects your fields into [validation rules](./12-requests-and-validation.md), so a
model can validate a request and build itself from it

```php
// In a controller
$product = Product::fromRequest($request);                                 // validated, primary key refused
$product = Product::fromRequest($request, ['agency_id' => $agency->id()]); // forced values win
$product = Product::fromRequest($request, forbiddenAttributes: ['price_dollar']);
$product->save();

$product = Product::fromArray($data);                                      // from an array

// The rules themselves, if you want them in a Request subclass
Product::toObjectParam();                                                  // fields + relations
Product::toObjectParam(nullable: true, withRelations: false);
```

`fromRequest()` throws an `InvalidArgumentException` when the request does not validate : let a
`Request` subclass validate it first. `fromArray()` does not refuse invalid data, so check data
coming from outside with `Product::toObjectParam()->validate($data)` before.

In those rules an auto-increment field is left out, a field is optional when its column is nullable
or has a database default, and so are the relations : only the columns an insert cannot do without
are required.

Returning a model (or a `Bunch` of models) from a controller is enough : the router converts it to
JSON, whole, every loaded relation and a password hash included. To choose what a model answers,
use a `ModelResource` — see
[Controllers and responses](./13-controllers-and-responses.md#shaping-what-a-model-answers).

A `Model`-typed parameter in a route callback is fetched from the slug automatically, with a `404`
when the row does not exist — see [Routing and middlewares](./11-routing-and-middlewares.md).

For a full CRUD API over a model, let your controller delegate to a `ModelAPI` instead of writing
the queries by hand — see [Model APIs](./19-model-apis.md).

## Reacting to a save

Every model is an event dispatcher, and emits `SavedModel` after each successful save — insert or
update. On an insert the model has already been reloaded, so the generated id and the database
defaults are available

```php
$product = new Product(['name' => 'screen']);

$product->onSaved(function (SavedModel $event) {
    Cache::getInstance()->delete('product-'.$event->created->id());
});

$product->save();
```

`SavedModel` carries the model (`$event->created`) and the `Database` it was saved with
(`$event->database`, which can be `null` on an update through the global instance). `onSaved()` subscribes to **one instance**, which is
what you want for a one-off follow-up, and what relations use internally to save bound children
after their parent. See [Events](./08-events.md) for the dispatcher itself.

## Faking models

`Product::factory()` builds models filled with fake values, for your tests and seeders — see
[Testing](./33-testing.md#faking-models).

## Sharing your types with the front-end

```bash
php do models:to-types
```

Writes a TypeScript file exporting one type per model, fields and relations included, plus a plural
array type (`Product` and `Products`), so your front-end reads the same descriptions as your
back-end. A nullable field becomes an optional property, a `DECIMAL` a `number`, a date a `Date`.

The file goes to `Storage/cube-types.ts` by default. Set another path, relative to your project, with
a `ToTypesConfiguration` in your `cube.php`

```php
new ToTypesConfiguration('front/src/types/cube-types.ts')
```

## Commands

| Command | Does |
|---|---|
| `models:generate [-a\|--apis]` | writes one model class per table, and with `--apis` a `ModelAPI` per model |
| `models:to-types` | writes the TypeScript types of every model |
| `migrate:migrate` | applies migrations, then runs `models:generate` — see [Migrations](./17-migrations.md) |
